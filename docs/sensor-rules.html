On your laptop: create the test rule.

01 / CHOOSE THE SOURCE

Open Rules

Sign in to the website, open your existing project, then choose Rules → Add rule. Select ESP32 Lab · Hardware readings, or your own ESP32 device name, and the existing Potentiometer / pot_raw input.

02 / USE AN EXAMPLE

Set 3000 / 2800 raw

Tap Use potentiometer example. It fills Above 3000 raw, reset at or below 2800, hold 0 seconds, cooldown 30 seconds and maximum sample gap 30 seconds. Review the explanation, then choose Save rule.

03 / INSPECT THE RESULT

Preview before saving events

Choose Preview test on your saved rule. Inspect the valid samples, triggers, resets and observation times. Previewing reads data and writes no events. Use Save test events only if you want that labeled test in the log.

On your phone: make a clear sample sequence.

Below → above → below

Keep the existing sensor upload option enabled. Turn the knob below 2800, then above 3000, then below 2800 again. Hold each position for at least one new sample. Use the current five-second sample interval and keep the sequence close together.

Upload queued readings when internet returns. On your laptop, choose Preview again. A qualifying high sample triggers the test; the next sample at or below 2800 resets it. A value exactly 3000 does not trigger an Above rule.

Read the time and quality labels

The test follows recorded sample times, not knob movement between samples. Phone-assigned timestamps stay estimated. Invalid or stale samples are excluded, and a gap over 30 seconds restarts this example's test state.

The preview uses the latest 100 loaded samples in the selected range and starts inactive. Earlier readings may be outside that window. It does not reconstruct a continuously running device rule.

Follow the result into your existing logs.

After Save test events, choose View event log. Hardware tests are labeled HARDWARE REPLAY; their observation time is shown separately from the event logging time. Warning events can be acknowledged through the existing control.

Your project's Analytics view can export the saved events. On Android, return to the normal dashboard, tap Sync, and check Logs. The event title begins Rule test triggered or Rule test reset.

A retry of the same uncertain event save reuses its IDs. Running Preview again creates a new test; saving that new preview deliberately adds another labeled test run.

If the preview has no trigger

There are no valid hardware samples

Confirm that the phone uploaded to the selected existing pot_raw stream. Use the latest time range, then Preview again. Data quality must be ok or estimated; stale, invalid, non-numeric and out-of-range-time records are excluded. A local phone reading does not appear in this website test until it has been uploaded.

There are samples, but the rule did not trigger

Check that at least one loaded value is strictly above 3000. Use hold 0 for the first experiment. A 30-second hold would require consecutive qualifying samples spanning that duration. Do not treat a missing sample as zero. After a reset, the example's 30-second cooldown can delay the next trigger.

The device or rule changed during the test

Close the preview, refresh Rules and review the source. Changed or paused rules cannot save events from an old preview. Hardware input membership is checked again before previewing and saving. Existing unsupported rule formats stay read-only.

I want an alarm while the website is closed

This release provides a manual historical test. It does not run on the board, in the phone background or as a cloud service. Keep that distinction when teaching or interpreting an event. Device-side automation needs its own firmware and physical acceptance.
